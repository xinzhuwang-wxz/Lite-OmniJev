## Ranked hypotheses and smallest discriminating observations

1. **Rank-shaped arithmetic plus BF16 recasts (plausible, unproven cause).** A changes output dimension16→64; B reduction dimension changes16→64 even though extra B columns are zero. BLAS can choose another kernel/tiling/accumulation path. FP32 adapter deltas can differ slightly; adding to BF16 base result and recasting at every layer may cross rounding thresholds and propagate through42layers. A zero prefix-extension contribution in real arithmetic does not guarantee bitwise-identical GEMM. Deterministic algorithms means repeatability for a fixed operation, not cross-shape equality. TF32off does not remove ordinary FP32 reduction-order or BF16 rounding effects. Logit delta.125 is consistent with coarse precision propagation but is not proof of BF16 final-logit dtype or this hypothesis.
2. **Historical-vs-fresh process difference (still open).** First compare fresh r16 with historical r16; if that alone reproduces the deviation, expansion has not been isolated. If fresh r16 repeats are stable, then compare fresh r16/r64 under the same actual preparation and recorded flags. Gradient owns this control; do not independently spend GPU repeating it.
3. **Conversion invariant problem (lower priority given CPU checks, still verify runtime load).** Prefixbitexact/Bnew0/scale2 strongly constrain algebra, but actual loaded tensor dtype/values, active adapters, variant and merged state should match receipt. Config auto mapping or dtype casts can alter loaded state after on-disk validation. This is a small summary check, not a new data pipeline.

If gradient's fresh crossrank difference persists, the smallest further localization is one actual decoder LoRA layer on a saved identical activation, comparing base result, first16 A channels, FP32 B output and post-add/post-cast output, with maxdiff aggregated. A pre-cast tiny difference that first becomes one BF16 ULP after casting supports hypothesis1; source-vs-source drift supports hypothesis2. Record actual base/A/B/result dtypes, autocast state, active/merged/variant state, CUDA TF32 and reduced-precision flags, torch/transformers/PEFT versions. ## Standard remedy boundary

Default PEFT adapter FP32 is already expected; simply saying “upcast adapters” is not a new remedy. Turning autocast_adapter_dtype off likely moves adapters towardBF16 and changes the experiment; no evidence it fixes the error. Zeroing both new A and B creates gradient-dead extra factors and defeats useful rank expansion. A custom rank-sliced forward, new head or engine patch would change the runtime contract and is not proposed. No tolerance relaxation or corrected output logits.

For numerical **reference only**, a standard full-FP32 base+adapter load, or independently SHA-bound FP32 safe_merge using existing S3 reference pattern, removes repeated BF16 residual recasts and rank-dependent serving factor execution after merge. It remains a hypothesis to test with unchanged tolerance and both source/expanded references. It costs more memory and does not retroactively prove BF16 initializer parity, training equivalence or S4 quality; existing S3 merged receipt is artifact-specific. Root should first use the pending fresh control; if BF16 crossrank still fails, retain failure and decide whether an explicit FP32 reference experiment is warranted rather than silently treating the expansion as function-preserving at runtime.
